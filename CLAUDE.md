# Kite

A fast, keyboard-first email client. Inspired by GotEmail, but goes further: local-first sync, Automations (built by example, no AI), Screener, Cleanup, send later, follow-up nudges, built-in sign-in codes, bring-your-own AI. Owner: Mark (South Africa, ZAR). What to build next is in [ROADMAP.md](ROADMAP.md).

## Product principles

- **AI is a layer, not the foundation.** Everything must work without AI (rules, local data, plain UI). Build every feature so AI can plug in later: data as typed records, actions as named verbs, specs as validated JSON. Don't wire new AI features until asked. **AI runs only when the user clicks a named action** (Describe an automation, Summarise, Draft with AI, Rewrite) and only sees the emails (or selected text) that action is about: never during sync, backfill or in the background, never extra emails as examples. The one exception is a rule's "Draft with AI" with that rule's "Allow AI" switched on (server/ai-drafts.ts): new mail only, one draft per conversation, the new email's fresh text only, spaced requests, pauses after errors, one switch pauses all, never sends. Every call passes an `AiPurpose` and is written to the privacy log. Every call also lands in the usage ledger (`ai_usage`, server/ai-usage.ts: tokens, cost, ok / error / blocked) and `generateJson` refuses it before anything is sent when its worst case (prompt + `maxOutput`) could cross the user's daily or monthly limit (`AiLimitReached`, HTTP 429, "Change it in Usage").
- **Local-first and private.** Mail lives in local SQLite; lists and search never wait on the network. Third-party calls (avatars, DNS-over-HTTPS, AI) send the minimum (domain, hashed email, matched emails only).
- **Users never see setup.** Kite ships its own OAuth client. Dev-only notices are gated on `process.env.NODE_ENV !== "production"`.
- **Onboarding is effortless:** type an email and Kite detects the provider (MX lookup for custom domains). Every error is explained plainly, with a retry.
- **Nothing irreversible without a clear action.** Destructive actions confirm inline. Moves have Undo (toast plus the `z` shortcut).

## Run

```bash
pnpm dev        # http://localhost:3100 (bound to 127.0.0.1)
npx tsc --noEmit -p . && pnpm lint && pnpm test   # run all three before every commit
pnpm test       # vitest (~15 s): test/unit (pure) + test/imap (IMAP and Gmail mode against scripts/imap-test-server.mjs on free ports); one file: pnpm test test/imap/gmail.test.ts, one test: -t "<name>"
pnpm desktop    # Tauri window on the dev server (reuses a running `pnpm dev`, else starts one)
pnpm desktop:build   # next build + bundled Node + hoisted prod install + `tauri build` -> src-tauri/target/release/kite.exe and bundle/nsis installer
pnpm desktop:release # desktop:build, then the installer copied to the desktop as "Kite Setup.exe" (~15 min; Rust recompiles only when src-tauri changes)
pnpm perf            # perf build (.next-perf, source maps) + bundle / browser / API / Gmail data numbers -> perf/results/latest.json (--only=bundle,browser,api,data,initial --idle=<min> --skip-build)
pnpm perf:check      # latest vs perf/budgets.json (fails when over) and perf/baseline.json (--save-baseline accepts a run)
node scripts/perf/quick.mjs --build --scenario=jk,search   # one fast UI check on the perf build (real copy, no sync): --profile / --trace / --spike / --serve; scenarios also paneresize, winresize, views, inboxtrip (--view=home), idle; --nofx=drift,grain,backdrop,shadow,mask,blurfade switches an effect off to see what it costs
```

- The desktop shell needs Rust (rustup, MSVC). If `cargo` isn't on PATH in an old shell, prepend `%USERPROFILE%\.cargo\bin`. Web edits hot-reload in the window; Rust edits recompile on save. `cargo check` in `src-tauri/` for Rust-only changes.

- Node 25, pnpm 11. Build scripts are allowed in `pnpm-workspace.yaml` (`allowBuilds`).
- `.env.local` holds `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (see `.env.example`). Redirect URI: `http://localhost:3100/api/auth/google/callback`. Restart the dev server after changing env.
- Local data lives in `data/` (git-ignored): `kite.sqlite`, the `avatars/` and `attachments/` caches, `assets/` (signature images) and `uploads/` (files on unsent mail). Deleting `data/` resets the app.
- The preview server config is `.claude/launch.json` (name `kite`).
- With no accounts connected the app runs on demo data (`src/lib/mail/demo-data.ts`), with onboarding on first launch.

## Feature additions (2026-10-19)

- Compose: local asset images become CID MIME parts; template recipients are opt-in; `lib/mail/snippets.ts` expands recipient variables in full compose and quick reply. Opening Drafts refreshes provider draft threads.
- Home holds what needs you (Today and Waiting on folded into it): To reply, Waiting on, Expected, your day; the sidebar's Home row counts replies owed plus what's due today.
- Search: 100-result pages with `nextOffset`, reader highlights in `components/mail/search-highlight.tsx`. `server/document-text.ts` locally extracts PDF, DOCX and text into `document_text` (account/message/part); `POST /api/files` explicitly indexes batches. Disconnect/reset clear this derived text. OCR and binary DOC remain unsupported.

Next.js 16 (App Router, Turbopack), React 19, Tailwind 4, Motion (`motion/react`), Hugeicons (`@hugeicons/react` + `@hugeicons/core-free-icons`, **the only icon library**), cmdk, react-resizable-panels v2, date-fns, zod 4, `node:sqlite` (FTS5), `@anthropic-ai/sdk`.

## Design system (keep consistent)

- **Sky, ink and paper:** behind everything is the sky (`bg-sky` + `on-sky` on the shell, `.sky-layer` for drifting cloud light, grain and night stars), following the local time (`data-sky`: dawn, day, golden, night; dark panes always get night). On it float cards: the panes (`rounded-2xl`, `pane-on-sky` shadow) follow light/dark via `[data-theme]`; the sidebar is one dark `ink-chrome` panel. `on-sky` turns the frame tokens white-on-sky, `ink-chrome` back to dark ink (toasts, popovers over panes, the compose dock). Blue is the accent; lime marks what's live (badges, selection), only ever as a fill behind ink text. Use the tokens (`bg-pane`, `text-pane-muted`, `bg-frame-hover`, `text-accent`, `bg-lime` and so on) from `globals.css`, never raw colours.
- **Calm navigation:** one row rhythm (36 px, 18 px icons, counts muted on the right), the selected row a quiet fill, small uppercase section headings; colour only where it means something (label colours on their tag icons). No outlined glass boxes stacked on each other.
- **Blur fade is the house transition.** CSS utilities: `blur-fade`, `blur-fade-up/down/left/right`, staggered with `style={{ "--i": index }}`. Motion presets: `blurFade({ x, y, blur, speed })`, `directionalBlurFade`, `springSnappy` in `src/lib/motion.ts`. Don't hand-roll new transitions.
- **Three motion speeds** (`spring.fast` / `moderate` / `slow` in motion.ts): fast for hovers, checks and toggles, moderate for menus, tabs, indicators and switches, slow for dialogs. Exits run a tier quicker (`exitFor`; `blurFade` exits fast by itself), so closing never drags. No new one-off durations.
- **Fonts:** body text uses `--font-ui`; message text, chat bubbles and compose use the `font-reading` utility (globals.css). Every font is variable and bundled (`app/layout.tsx`: next/font Google, open-source (OFL) only, since signed releases may carry only open-source parts), only the defaults (Geist interface, Inter reading) preloaded; Instrument Serif (italic only) is the accent for one word in a heading (`font-accent`, AccentTitle). **No monospace anywhere** (`--font-mono` and `code`/`kbd`/`pre` use the interface font; digits that must line up use `tabular-nums`). The font variables sit on `<html>`.
- **Icons:** `<Icon icon={XIcon} size={16} />` from `src/components/icon.tsx`, with Hugeicons only. Real brand marks come from `brand-logos.tsx` (Google, Microsoft; iCloud, Zoho, GMX from Simple Icons, CC0) and `ai-logos.tsx` (AI providers, generated from `@lobehub/icons-static-svg`, MIT).

No dead zones in gaps, gap clicks go to the lit row. Rows spread `FLUID_ITEM`, set their own rounding and style hover with `data-[lit]:` instead of `hover:`; a row's own transition list must include `background-color` at 150 ms. Small controls inside spread `FLUID_IGNORE`. `tone`: `frame`, `lift` (sidebar popover), `pane`, `pill` (pill tracks). One FluidList per group. `axis="x"` for pill tracks and tabs, `axis="xy"` for card grids; `follow="[data-selected=true]"` for keyboard-driven lists (cmdk, pickers). Pills: the track is the FluidList, the selected pill eases to semibold.
- **Selections merge:** ticked rows next to each other in the message list are one shape (`joinAbove`/`joinBelow` square the corners where they meet). Keep that for any new multi-select list.
- **Scrollers get `scroll-fade`** (globals.css, scroll-driven, no JS): content fades at an edge only while there's more that way. Put it on the element that scrolls.
- **Selects:** use `Select` (`src/components/ui/select.tsx`), never a native `<select>`.
- **Shared feedback:** copy buttons use `useCopy` + `CopyIcon` (copy glyph morphs into a tick), switches use `Switch`/`SwitchTrack`, AI waits use `Thinking` (pixel grid, steps rolling up with a blur in the `shimmer-sweep` text, elapsed timer; `timer={false}` inside buttons; it takes the text colour, so set the wrapper to `text-pane-fg` on panes); every other wait uses `Spinner` (ui/spinner.tsx: faint ring + running arc in the text colour, beside the busy label in buttons), never a hand-rolled one. AI limits show as `UsageRing` (ui/usage-ring.tsx: success / warning / danger by share); AI errors render through `AiErrorText` (components/ai-usage-link.tsx: "Usage" links to Settings → AI).
- **Buttons:** round outlined icon buttons (`CircleButton`), pill inputs and pill segmented controls with a sliding `layoutId` indicator.
- **Every icon-only button gets a `Tooltip`** (shared bubble: 320 ms first delay, then glides and slides directionally). Pass `shortcut="<action>"` so the tooltip shows the user's current binding.
- **Buttons:** a new conversation action that could sit on a button goes in lib/buttons.ts (BUTTON_ACTIONS, BUTTON_INFO), button-icons.ts and the reader's `readerActions` (and `hoverButton` if it works on a row without opening it); never hard-code a toolbar button.
- **Shortcuts:** add new actions to `SHORTCUT_DEFINITIONS` in `src/lib/shortcuts.tsx` and handle them in `mail-app.tsx`. Never hard-code keys.
- **Layout is width-agnostic:** new UI must not hard-code wide widths or assume three panes fit. Use flex/min-w-0, truncate, and widths that can shrink; container queries (`@container`, `@max-[520px]:`) for a pane's own width. lib/layout.ts holds the breakpoints: the sidebar is full from 1024 px, a rail from 640 px, a drawer below; the list and the reader sit side by side only when both fit (`LIST_MIN_PX` + `DETAIL_MIN_PX`), else one at a time (Enter / Backspace). Compose fills the screen and dialogs take the width below 640 px. Touch screens get finger-sized controls with the `touch:` variant (globals.css, `pointer: coarse`) on shared controls.
- **Charts:** a single series per chart in one colour, values labelled at the tips (contrast is below 3:1), and every chart keeps a table view. Text uses text tokens, never the series colour.

## Conventions and gotchas

- **Writes from the browser:** every POST/PATCH/DELETE route calls `rejectCrossSite(request)` (same-origin plus JSON content type). Keep it that way. File uploads use `rejectCrossSite(request, { binary: true })` (raw `application/octet-stream`, name in `x-file-name`).
- **Message bodies are markup, never HTML:** `**bold**`, `*italic*`, `[label](url)` (same as kite-design/1 text), plus `- ` / `1. ` lists and `\` escapes. The editor serializes the DOM to markup; `body.ts` renders it. Queued messages without `format: "markup"` are plain text (escape with `escapeMarkup`).
- **Compose = `ComposeDraft`:** the same zod record is autosaved as a Gmail draft, sent, or queued. Replies/forwards carry a `quote` (content added at send time from the local copy); forwards and files picked from "Attach from your files" carry `{ type: "message", accountId?, messageId, partId }` refs (no `accountId` = the draft's account; another account's file is read with that account's access). Gmail sends go through the media upload endpoint (35 MB) with JSON metadata. Gmail caps a message at 25 MB encoded (about 18 MB of files); explain limits with `attachmentLimitError`.
- **Fill & sign:** user-driven only (Kite never fills or signs by itself). "Fill from my profile" fills only on request, only exact rule matches (`PROFILE_RULES`) in places still empty (a remembered layout wins), never checkboxes, radios, signatures or free-text questions; two places on a page asking the same thing are left alone. Profile values stay local and out of logs. The original attachment is never changed: the copy is a new `upload` (named "(signed)"/"(filled)") and "Reply with signed copy" only opens a reply (`startCompose` with `{ threadId, attachments }`). pdf.js and pdf-lib load only inside the editor, or in the preview when the sender has remembered layouts (to check for a match); pdf.js alone also draws file cards' first-page thumbnails (files/pdf-thumb.ts: once a card is on screen, one PDF at a time, up to 10 MB, kept for the page load). Positions are PDF user space; text is written in Helvetica (WinAnsi), so check `unsupportedCharacters` before saving. Locked (encrypted) or unparseable PDFs get an image-based copy; XFA is dropped from the copy; an existing digital signature needs "Edit anyway". Remembered layouts are offered only for a single confident match (sender, page sizes, print similarity) and only place things for review; form text reaches the server as lines, is hashed with a per-install salt and never stored or logged.
- **Designed mail:** signatures, designed emails (`ComposeDraft.design`, sent instead of `body`) and templates are `Design` JSON, never stored HTML. Outgoing mail with a design or signature is multipart/related(alternative(text, html), inline images, one per asset); `buildMime` in server/mail/mime.ts builds it. Compose's Write mode (markup) stays the default. See ROADMAP "Designed mail".
- **Attachments:** Gmail attachment ids change between fetches, so files are addressed by `partId` and looked up again on download. The route serves only viewable types inline (images, PDF, text, audio/video); everything else downloads as octet-stream, always with `nosniff` and a sandbox CSP (except inline PDFs). Inline images (`inline: true`) are hidden from file lists.
- **Quotes are folded, never dropped:** `splitHtml` guarantees `fresh + signature + quoted === html`; the reader renders slices of the original in the sandboxed frame. When unsure, everything stays fresh. Check changes against fixtures (Gmail, Outlook web/desktop/mobile, Apple, plain text, newsletters unchanged) and keep scans linear.
- **Local overrides:** chat view, mute, pin, note, local subject and reply tracking's Done / Dismiss live in `thread_overrides` keyed by Kite thread id, loaded with `/api/settings` and applied on the client (`applyOverride`). Sync and "Reset local copy" never touch them; the FTS row includes the local subject and note (`reindexThread` after a change).
- **Account names:** show accounts with `accountName(account)` (lib/mail/types.ts: local nickname, then Google name, then address), never `account.email` as a label. The nickname lives in `accounts.nickname`, set only in Settings → Accounts.
- **Rules engine = Automations:** everything Kite does to mail by itself is an automation, stored as a rule (server/rules.ts) with typed verbs (lib/rules/spec.ts): When (`when`: `new_mail`, `sent` (mail you send, from Kite (deliver screens it) or anywhere; "sender" fields and `senders` read who it went to) or `schedule` (a day each week or month, no email: `expect` per person, `pack`); `TRIGGER_VERBS` says what each can do; `delay`: new mail only, wait before acting (notify still now); search + conditions, incl. `senders`: the sender is one of) → Read (`fields`) → Check (`checks`) → Do (verbs whose text takes `{field}` blanks); `referenceProblem` keeps the parts consistent. Read works on the stored copy (the body is downloaded first on arrival when a field needs text; Run on existing mail reads the body Kite has, else the preview); don't add hard-wired automatic behaviour, add a verb or a preset. Kite never invents rules: only presets (fixed in lib/rules/presets.ts) and rules the user made. Rules run only on conversations with new messages during incremental sync (`screen`), never on initial sync, and on existing mail only from "Run on existing mail". Gmail changes touch only the new messages (your earlier choices win); actions never re-trigger rules; Undo of a run makes that rule leave the conversation alone. Matching is in memory (`matchesSearch` with `MatchFacts`: is:/in: read labels); bodies are fetched only when a rule's other terms already match. Rules that change something are logged in `rule_runs` (30 days); a notify alone isn't. The Screener is the "Hold new senders" preset (off by default): sync records every sender it sees as `allowed` after the rules run, so only someone with no `senders` row is new. Stay outside the engine: snooze wake-ups, send later, follow-up nudges, category tabs and Codes. `expect` waits for an answer (Waiting on's Expected): its requests and nudges are ready for one tap, and Kite sends them itself only with that step's `auto` switch, which the user turns on (same for `pack`, else a draft); it's new mail only (`NEW_MAIL_ONLY`). `prepare_reply` only stores text (blanks filled at match time from the message, never AI); the reader's quick reply shows it with "Prepared by <automation>" and Discard, and only moves it in while the box is empty. It's never sent by itself, and "Run on existing mail" skips it like notify and screen (`NEW_MAIL_ONLY`). "Also run in Gmail" (`Rule.gmail`, off by default, only when `gmailFilterFor` says the whole rule translates: no conditions, Gmail verbs only, no Stop here, no in:/is:/label:) keeps one Gmail filter per covered account (skipped where the label is missing); Kite still runs the rule on arrival, logs what the filter already did as the filter's work (Undo reverses it, but the filter keeps acting on new mail), and does whatever is left.
- **All mail** (mailbox id `archive`, kept because the client's "moved out of the Inbox" patches use it) is everything but Trash, Spam and drafts, like Gmail's All Mail; its Inbox conversations keep mailbox `inbox`. Kite can't tell who archived something (you, a phone, a filter, a rule), so there's no "Archive" view. The `e` action is still Archive (out of the Inbox), and `in:archive` searches for that.
- **Spaces are Kite's own** (lib/spaces.ts, server/spaces.ts): places for mail across every account, with pockets inside (four levels). Only on this computer: no provider sees them, sync and "Reset local copy" never touch them, Disconnect takes that account's conversations out. A conversation can be in several; a space's list includes its pockets'. "Move to space" is add + archive (the archive is the only thing the provider sees). The automation verb is `space` (rule-verbs.ts, undoable); Kite only offers "Always for <sender>" after the user put 3+ of their conversations there itself, and makes the rule only on that tap. New conversation actions go in the actions menu (use-thread-menu.tsx), not the hover row.
- **Per-person state:** VIP flags and private notes live in the `people` table (loaded with `/api/settings`, changed with `POST /api/people`). Kite never marks anyone VIP by itself; sync and "Reset local copy" never touch it. Notes stay out of logs. "Always load images" (`images`) lives here too and is set only from the privacy chip.
- **Privacy in the reader:** tracking pixels are stripped when a message is stored (each provider's convert step, `stripTrackers`); link cleaning and image holding happen at render time (lib/mail/privacy.ts), so the stored HTML is never changed by them. Link cleaning only removes known tracking params or unwraps redirectors whose target is a plain parameter, never touches sign-in / confirm / unsubscribe links, and keeps the rest of the address byte for byte. Misleading links (text names one site, href another) get a title and outline (`protectLinks`); `Message.auth` (Gmail's Authentication-Results) drives "Verified sender" / "Sender not verified" in the shield. Explain in one short line beside the action, never a paragraph.
- **Privacy is a feature; keep it true.** Anything that leaves the computer (other than the mail provider) goes through `logSent` / `countSent` (server/privacy-log.ts) so Settings → Privacy can show it, and needs an off switch plus a line in PRIVACY.md (SignPath's terms for signed releases; the installer shows that file). Everything bundled must be open source (no fonts or assets under other licences). Web pictures only for company domains (never personal addresses). Secrets are sealed (server/secrets.ts); never store a token or key in plain text. Mark new UI that shows who wrote, what about, bodies or codes with `data-sensitive` so screen privacy (Shift+P) blurs it. Disconnect and "Erase everything" must remove all data tied to what they erase (rows, caches, the search index via `compactSearchIndex`).
- **Translation stays on this computer.** Message text goes only to Kite's own server (detection) and the worker; the network sees only the one-time downloads of the engine and languages from Mozilla, each after the user says yes, hash-checked and logged. The CSP allows `'wasm-unsafe-eval'` for it (compiling wasm, not eval of script). No AI.
- **Notifications go through `shouldNotify`** (lib/notify-rules.ts; kinds mail / code / scheduled / meeting): never call `notify()` without a decision, and always pass the plain version (`notifications.showContent` is off by default: "New mail", "Sign-in code ready", no sender, subject or code; the desktop toasts and tray follow it, the tray never shows a code). New mail notifies only when a rule's notify verb says so (now, or batch: held while Kite is hidden and summarised at the next batch time when batches are on); codes come now.
- **Derived fields:** `Message.preview` (new text for list rows) and the FTS body (fresh text, plus forwarded content) come from quotes.ts in `upsertRecord`. When `textOf`/`previewOf` change, bump `DERIVED_VERSION` in store.ts so `upgradeDerived` redoes stored threads once.
- **Per-message read state:** `Message.unread` mirrors Gmail's UNREAD label; the reducer's `select` captures `state.unseen` before the thread is marked read, and the reader opens those messages under a "New" divider. "Mark unread", snooze wake-ups and follow-up nudges mark only the newest message from someone else (`unreadTarget` in store.ts), and local INBOX / UNREAD changes skip your own sent mail and drafts. Metadata refreshes keep their own labels over the stored copy (`mergeMessages`); unread threads missing it are refetched in batches (`backfillReadState`).
- **The inbox's tabs are the provider's** (lib/mail/sides.ts): Gmail's Primary / Promotions / Social / Updates, Outlook's Focused / Other, one list for accounts without tabs; Kite never re-sorts the inbox by guessing from addresses. `state.side` is a `Category`, tab shortcuts `1`–`4` by position. Home (`home`) is what needs you, not a second inbox.
- **Where Kite opens:** preference `startView` (Settings → Appearance: Last screen / Home / Inbox); the last screen is kept in localStorage `kite-last-view` (lib/start-view.ts `rememberView` / `startViewFor`), applied once when settings first load.
- **Lists are slim:** lists, search filters and the files list read `threads.list_data` (`LIST_DATA` / `LIST_COLUMNS` in store.ts), a body-free copy kept by SQLite triggers (`listCopy` in db.ts, which must cut the same fields as `hydrate`; bump the trigger names when it changes). Counts use `countThreads` (SQL only). Never select `t.data` for a list. Bodies come from `GET /api/mail/threads/[id]` (local first, then Gmail).
- **Kite threads are not always Gmail threads.** Ids are `${accountId}:${key}`; the key is the Gmail thread id, or `${gmailThreadId}~${firstMessageId}` for a conversation split off locally. API paths and ops take the key (`threadKey(thread)`), never `remoteId`. A merged conversation holds messages of several Gmail threads (`Message.remoteThread`, `remotesOf`). Every store of a Gmail thread goes through `placeRemote` (message_moves, thread_merges, replies follow their parent), so sync re-applies splits and merges. Ops use `opTargets`: threads.modify for Gmail threads held whole, messages.batchModify for parts. Snoozes are stored under the key. Look Gmail threads up with `rowsHolding` / `remoteMessages`, not `${account}:${remoteId}`. Messages keep their own `labels` and `subject`.
- **Sync engine and hot reload:** the timer calls `engine.tick`, which is reassigned on module load. Restart the dev server if engine state looks stale. Routes can load their own copy of a server module, so any in-memory cache that sync reads and a route writes (like the rules cache) lives on `globalThis`.
- **Schema changes:** the schema is the `CREATE TABLE IF NOT EXISTS` statements in db.ts; there are no migrations. A new column goes in its CREATE, and existing local databases (Mark's `data/`, `data-demo/`) get the same `ALTER TABLE ... ADD COLUMN` once, run by hand after asking; mail tables can instead be rebuilt with Reset local copy.
- **No compatibility code (in development, one user):** no readers for old data shapes, renamed keys or old builds. Change the shape, convert stored data once by hand (or reset), and delete the old path in the same change.
- **Providers differ; declare, don't assume.** Whether a label is a tag (many per message, stays where it is: Gmail labels, Outlook categories) or a folder (one per message, choosing one moves it: Outlook/IMAP folders) lives on the label (`MailLabel.kind`, `labels.kind`), never on the provider; the provider spec (`lib/mail/providers.ts`) holds the words per kind, nesting and system ids. What a change does to a message is `applyLabelChange` (picker, `runLabelChange`, rules engine all use it); folder moves go per message so Undo puts each one back where it was. UI wording and behaviour come from `providerSpec(account.provider)`; provider calls go through an adapter (`server/labels.ts`). Label changes only accept the account's own labels (`ownLabels`), never system mailboxes.
- **Sign-in comes in two kinds** (`MailProvider.auth`): OAuth (`OAuthAuth`: redirect + callback, tokens in `tokens`) or a password (`PasswordAuth`: `signIn` checks the servers first, `save` stores the sealed secret; Settings → Accounts' Reconnect opens Kite's form). Push is optional (`MailAdapter.watch`): the engine keeps one per account and skips the quick check for it.
- **Mail providers are plug-ins.** Each lives in `src/server/providers/<name>/` and implements `MailProvider` (server/mail/provider.ts); everything else reaches it through `providers/registry.ts` (`providerFor(account)`, `mailOf(account)`), never by importing its files, and providers never import each other (both enforced by `no-restricted-imports` in eslint.config.mjs). Shared code goes in `server/mail/`. Adapters translate to Kite's model: labels in Kite's names (lib/mail/mailboxes.ts) plus the account's own label/folder ids, ids matching `REMOTE_ID`. What isn't universal is optional and declared (`labels` (with `reconnectFor`: a missing optional permission, shown in Settings → Accounts), `filters`, `contactPhotos`; UI wording from `providerSpec`), never faked. A provider with `mail: null` signs in but isn't synced (`mailAccounts()`). User-visible wording names the account's service (`serviceName(account)`: the IMAP service like "iCloud Mail", else `providerSpec(p).name`; `serviceNames` for several), never "Gmail" in shared UI. Adding one: a folder, a line in the registry, an entry in lib/mail/providers.ts, its sign-in slug in lib/mail/connect.ts.
- **Meeting invites:** a message with a calendar part (`Message.calendar`, a hidden "invite.ics" attachment for nameless text/calendar parts) or an Outlook event message gets `Message.invite` when its conversation opens (`withInvites`). Answering is only the user's click: in the account's calendar when it has one (`calendarFor(account)` in the registry: the provider's `calendar`, if its `offered` allows this account) and the permission (preference `calendar`, Settings → Accounts or Connect on the card; Google `calendar.events`, Microsoft `Calendars.ReadWrite`), else an iTIP REPLY email to the organiser (IMAP, incl. Gmail over IMAP until its optional Google sign-in is connected; Gmail when the event isn't in Google Calendar or the user picks "Answer by email"). Answers sent from Kite are kept in `invite_replies`. The same permission (Settings → Accounts "Use your calendar") gives Today the account's events: a read-only local copy (server/events.ts) synced on the tick, gone when the preference is off, on Disconnect and Erase everything. Kite adds an event only from the "Add to calendar" form the user saves; it never reads the body for dates (only text the user selected). Accounts with no provider calendar Kite can reach get the mail calendar (server/mail-calendar.ts) under the same switch: events only from calendar files in stored mail, your answer from invite_replies or your own iTIP REPLY in Sent, events added in Kite stay in Kite (`CalendarEvent.source` "mail" / "kite", `Account.mailCalendar`; the UI says so). A real calendar always wins (`eventSource`), so nothing shows twice; invite answers still go by `calendarFor` only.
- **Optional Google scopes** (contact photos; `gmail.settings.basic` once any rule has "Also run in Gmail"; `calendar.events` once "Use your calendar" is on) are requested only when their setting is on (`scopesFor` in providers/gmail/oauth.ts, incremental auth). Check `hasScopes` before calling the API and keep working without it; the UI offers Reconnect.
- **Gmail over IMAP's Google extras:** the account's photo, calendar and contact photos come from an optional Google sign-in added in Settings → Accounts ("Connect Google", `permissionHref(account)` on the client; `Account.googleLink`: undefined = not offered), never needed for mail. All through `shouldNotify`.
